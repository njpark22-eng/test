# 엔드포인트 계약: 가상 계측 데이터 저장과 결과 이력

기존 `GET /`, `GET /api/analyze`(001)는 그대로다. 아래는 추가되는 것이다. 수정·삭제 엔드포인트는 만들지 않는다.

## 공통

- 로그인과 토큰이 없다. 쓰기(`POST`)와 읽기(`GET`) 모두 공개이며 남용은 크기·횟수·형식 검증으로 제한한다.
- 오류 본문은 `{"error": "한 줄 안내"}` 형식이다. 안내는 무슨 일이 생겼고 무엇을 하면 되는지 쓴다.
- `DATABASE_URL` 값은 어떤 응답에도 넣지 않는다.

| 상태 | 의미 |
|---|---|
| 413 | 파일 1개 1 MB 초과 또는 합계 4 MB 초과 |
| 422 | 형식·값 검증 실패 (엑셀 형식, 샘플링 주파수, 채널 수, rpm, 볼 개수) |
| 429 | 시간당 30회 초과 |
| 503 | 저장소(`DATABASE_URL`)가 설정되지 않았거나 연결 실패 |

## `GET /api/config`

화면이 쓰는 고정 설정.

```json
{
  "limits": {"max_file_bytes": 1048576, "max_total_bytes": 4194304, "max_channels": 5, "runs_per_hour": 30},
  "thresholds": {"rms_limit": 4.5, "lowfreq_noise_limit": 20.0, "ratio_2x_over_1x": 0.5, "ratio_bearing_over_1x": 0.7}
}
```


## `POST /api/inspect`

파일 하나를 읽어 검증하고 자동 rpm과 데이터 앞부분을 돌려준다. 저장하지 않는다.

- 요청: 멀티파트, 필드 `file`
- 성공 200

```json
{"samples": 10240, "fs": 5120.0, "rpm_detected": 1800, "preview": [[0.0, 0.12], [0.000195, 0.31]]}
```

`preview`는 앞 20행이다. 실패는 413/422.

## `POST /api/runs`

파일을 검증하고 분석한 뒤 원본과 결과를 저장한다.

- 요청: 멀티파트. 채널 수만큼 `rpm`(정수)과 `balls`(정수, 생략하면 모두 1)를 보낸다. 채널의 파일은 새로 올리거나(`files`) 저장된 파일을 고른다(`file_ids`).
  - `file_ids`: 채널 순서대로 저장된 파일 번호 또는 빈 문자열(새로 올린 파일 사용). 생략하면 `files` 개수만큼 모두 새 파일이다.
  - `files`: `file_ids`가 빈 채널의 개수만큼, 채널 순서대로 올린다. 한 요청은 1~5채널이다.
- 검증: 크기, 엑셀 형식, 샘플링 주파수 5,120 Hz, rpm 0 초과 20,000 이하, 볼 개수 1~100 정수, 입력 rpm의 1X 성분이 최대 피크의 20% 이상(아니면 422와 `{"error", "channel", "detected_rpm"}`)
- 성공 201: 아래 상세 응답과 같은 본문
- 원본과 결과는 한 트랜잭션으로 저장한다. 실패하면 아무것도 남기지 않는다.

## `GET /api/files`

저장된 원본 파일 목록, 최신순, 최대 100건. 파일 내용은 넣지 않는다.

```json
{"files": [{"id": 5, "sha256": "...", "channel": "CH5", "size_bytes": 173747,
            "filename": "CH5.xlsx", "uploaded_at": "2026-11-13T05:00:00+00:00"}]}
```

## `GET /api/files/{id}`

저장된 파일의 자동 rpm과 앞 20행(저장하지 않음). 없는 번호는 404.

```json
{"id": 5, "sha256": "...", "filename": "CH5.xlsx", "samples": 10240, "fs": 5120.0, "rpm_detected": 2400, "preview": [[0.0, 0.12]]}
```

## `GET /api/runs`

저장된 분석 실행 목록, 최신순, 최대 100건.

```json
{"runs": [{"id": 12, "created_at": "2026-11-13T05:00:00+00:00", "channel_count": 5,
           "verdicts": [{"channel": "CH1", "verdict": "재계측 권장"}]}]}
```

## `GET /api/runs/{id}`

```json
{"id": 12, "created_at": "...", "thresholds": {"rms_limit": 4.5, "lowfreq_noise_limit": 20.0,
  "ratio_2x_over_1x": 0.5, "ratio_bearing_over_1x": 0.7},
 "channels": [{"channel": "CH1", "rpm": 900, "balls": 1, "sha256": "...", "r": {}, "verdict": "재계측 권장",
               "f": [], "amp": []}]}
```

`r`은 저장된 `analyze_signal` 값 그대로, `f`/`amp`는 저장된 스펙트럼이다. 없는 `id`는 404.

상세 응답에는 저장되지 않고 요청할 때 만들어지는 `insight`(채널마다)와 `summary`(실행 전체)가 붙는다. 저장된 판정을 설명할 뿐 다시 계산하지 않는다.

```json
{"channels": [{"channel": "CH4", "insight": {
    "basis": ["최대 피크 RMS 11.31 mm/s(20.0 Hz)를 기준 4.5 mm/s와 비교: 기준 초과", "...", "판정: ... (규칙 4)"],
    "graph": ["세로줄은 1X 20.0 Hz, 2X 40.0 Hz이고, 점선 가로줄은 기준 4.5 mm/s입니다", "가장 큰 피크는 ..."],
    "meaning": "해석 한두 문장", "action": "조치 한 문장"}}],
 "summary": {"headline": "5채널 중 정상 1, 재계측 권장 1, ...",
             "priorities": ["CH4 발란싱 요망: 최대 피크가 기준의 2.5배", "..."],
             "note": "규칙 기반 추정입니다. 원인은 현장 점검으로 확정하세요."}}
```

- `basis`는 5줄: 최대 피크 RMS 비교, 1X·2X 값, BPFO(또는 베어링 미사용 설명), 저주파 노이즈, 판정과 해당 규칙. 기준 숫자는 저장 당시 기준값을 쓴다.
- `priorities`는 기준 초과 배수가 큰 발란싱·정렬 채널 순, 그다음 베어링 점검과 재계측 채널이다.

## 화면 경로

| 경로 | 내용 |
|---|---|
| `GET /upload` | 올리기 화면. '가상 데이터만 올리세요. 실제 계측 데이터는 금지'를 항상 표시 |
| `GET /runs` | 이력 목록 |
| `GET /runs/{id}` | 같은 HTML이 상세(요약, 판정 근거, 인사이트, 그래프 읽기)를 보여 줌 |

## 계약 검증 (테스트)

- 토큰 없이 쓰기·읽기 모두 동작하고, 응답에 `write_enabled`가 없다.
- 정상 업로드 5개 → 201, 판정이 기대값, 저장된 해시가 올린 파일의 SHA-256과 같음.
- 크기 초과 413, 잘못된 형식·rpm·볼 개수·샘플링 주파수 422, 횟수 초과 429, 저장소 없음 503.
- 같은 파일 재업로드 → 원본 행이 늘지 않고 결과 행은 늘어남.
- 저장된 파일 목록(최신순, 내용 없음), `file_ids`로 다시 올리지 않고 분석(원본 수 그대로), 새 파일과 섞기, 없는 번호 404, 숫자 아닌 번호 422.
- 이력 상세의 모든 채널에 `insight`, 실행에 `summary`가 있고 저장소에는 저장되지 않는다.
- `PUT/PATCH/DELETE`는 405.
