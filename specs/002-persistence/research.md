# 조사 결과: 가상 계측 데이터 저장과 결과 이력

조사일 2026-11-13. 미해결 항목은 아래 결정으로 정리했다. `확인 필요`는 배포 환경에서 직접 검증한다.

## 1. 저장소와 드라이버

- **결정**: Neon Postgres를 `psycopg`(3.x, binary)로 연다. 요청마다 연결을 열고 닫는다. 연결 주소는 Neon의 풀링(pooler) 주소를 쓴다.
- **근거**: 서버리스 함수는 연결을 오래 쥘 수 없어 풀러를 거치는 것이 안전하다. 순수 SQL로 충분해서 ORM은 쓰지 않는다.
- **환경변수**: `DATABASE_URL`(연결 문자열), `WRITE_TOKEN`(쓰기 토큰). 값은 코드·로그·응답·저장소에 남기지 않는다. 이 개발 셸에는 둘 다 없어서 실제 DB 접속 테스트는 실행하지 않았다(`확인 필요`).
- **검토한 대안**: Neon 서버리스 드라이버(HTTP) — Python 공식 지원이 약하다. SQLAlchemy — 이 규모에 과하다.

## 2. 추가만 가능한 저장

- **결정**: 테이블 4개 모두 `BEFORE UPDATE OR DELETE` 트리거로 예외를 일으켜 수정·삭제를 막는다. 앱 코드에도 수정·삭제 함수를 만들지 않는다. 스키마는 `CREATE TABLE IF NOT EXISTS`와 `CREATE OR REPLACE`로 멱등하게 만들어 처음 DB를 쓸 때 한 번 적용한다.
- **근거**: 앱 버그나 직접 접속으로도 원본·결과가 바뀌지 않게 하려면 DB가 막아야 한다(원칙 I). 
- **확인 필요**: `CREATE OR REPLACE TRIGGER`는 Postgres 14 이상이다. Neon의 버전이 낮으면 `DROP TRIGGER IF EXISTS` 후 생성으로 바꾼다. `TRUNCATE`와 테이블 `DROP`은 트리거로 막히지 않으므로, 쓰기 계정 권한에서 제외하는 것을 권한다(운영 안내에 적는다).

## 3. vibe_agent 전역 상태와 동시 요청

- **문제**: `analyze_signal(name)`은 전역 `SIGNALS[name]`, `RPM[name]`, `BALLS[name]`을 읽는다. 업로드 분석에서 이 전역을 바꾸면 동시 요청이나 기존 `/api/analyze`(`for ch in va.SIGNALS`)와 충돌할 수 있다(딕셔너리 순회 중 크기 변경 오류).
- **결정**: 고유 임시 키(`UP-<무작위>-CH1`)로 넣고 `analyze_signal` 호출 직후 지운다. 전역을 건드리는 모든 코드(업로드 분석과 기존 `/api/analyze`)는 `api/analysis.py`의 하나의 잠금 아래에서 실행한다. 결과의 `channel`은 실제 채널 이름(`CH1`)으로 되돌린다. `vibe_agent.py`는 수정하지 않는다.
- **근거**: 판정 로직을 다시 구현하지 않으면서(원칙 II) 동시성 문제를 피하는 가장 작은 방법이다.
- **검토한 대안**: `analyze_signal` 복사 — 원칙 II 위반. 프로세스 분리 — 과하다.

## 4. 기준값 고정과 기록

- **결정**: 기록할 기준값은 `{rms_limit: va.RMS_LIMIT, lowfreq_noise_limit: va.LOWNOISE_LIMIT, ratio_2x_over_1x: 0.5, ratio_bearing_over_1x: 0.7}`다. 앞의 둘은 `vibe_agent`의 상수에서 읽고, 뒤의 둘은 `rule_verdict`가 함수 안 숫자로 갖고 있어 읽을 수 없으므로 `api/analysis.py`에 고정값으로 두고 **경계 테스트**로 `rule_verdict`와 일치함을 확인한다(0.5 → 정렬 요망, 0.49 → 발란싱 요망, 0.7 → 베어링 점검 요망, 0.69 → 정상).
- **근거**: 코드를 수정하지 않고(기준값 고정) 기록의 정확성을 테스트로 지킨다. `vibe_agent.py`의 값이 바뀌면 테스트가 실패해 알려 준다.

## 5. 업로드 방식과 한도

- **결정**: 멀티파트 폼(`python-multipart`)으로 받는다. 한도는 파일 1개 1 MB, 한 요청 합계 4 MB, 채널 1~5개. 본문 합계 제한은 Vercel 함수의 요청 크기 제한(약 4.5 MB, `확인 필요`) 안에 둔다.
- **근거**: 가상 데이터 엑셀이 약 170 KB(5개 합계 약 0.9 MB)라 여유가 크다. 크기 검사는 읽은 바이트 길이로 한다(헤더를 믿지 않는다).
- **흐름**: 파일을 고르면 `/api/inspect`가 자동 rpm과 데이터 앞부분을 돌려주고(저장 안 함), 분석 실행 때 `/api/runs`가 같은 검증을 서버에서 다시 한다.

## 6. 횟수 제한

- **결정**: `analysis_runs`에서 최근 1시간 행 수를 세어 30회 이상이면 거부한다. 별도 테이블이 없다. `/api/inspect`는 저장하지 않으므로 이 제한에 포함하지 않고, 토큰으로만 막는다.
- **근거**: 토큰이 하나뿐이라 전역 한도로 충분하다. 요청 수 기반 제한이 필요하면 후속 작업으로 둔다.

## 7. 쓰기 토큰

- **결정**: 요청 헤더 `X-Write-Token`을 환경변수 `WRITE_TOKEN`과 `hmac.compare_digest`로 비교한다. `WRITE_TOKEN`이 비어 있으면 쓰기를 모두 거부한다(안전한 기본값). 올리기 화면은 토큰을 입력받아 `sessionStorage`에만 보관한다(브라우저 탭을 닫으면 사라짐).
- **근거**: 로그인 없이 쓰기를 제한하는 가장 단순한 방법이다. 토큰 값은 응답과 로그에 쓰지 않는다.
- **주의**: 토큰은 HTTPS로만 전달된다(Vercel 기본). 로컬 개발에서는 HTTP다.

## 8. 결과 저장 내용과 그래프

- **결정**: 채널 결과에 `analyze_signal` 전체(JSONB), 판정, rpm, 볼 개수, 스펙트럼(0~600 Hz의 주파수·진폭 배열, JSONB)을 저장한다. 상세 화면은 저장된 값으로 그래프를 그리며 원본을 다시 읽지 않는다.
- **근거**: 과거 결과를 다시 계산하지 않는다는 요구(FR-006)와 상세 응답 속도를 함께 만족한다. 스펙트럼은 채널당 약 15 KB다.

## 9. 화면 구조

- **결정**: 올리기(`/upload`), 이력 목록(`/runs`), 상세(`/runs/{id}`, 같은 HTML)를 추가하고 기존 `/`(판정 화면)는 유지한다. 공통 CSS·JS를 `api/shared.css`, `api/shared.js`로 빼서 중복을 없앤다.
- **근거**: 색 토큰과 스펙트럼 그리기를 한 곳에서 관리해야 디자인 규칙이 어긋나지 않는다.

## 10. Vercel의 `api/` 폴더 규칙 (배포 실패로 확인)

- **문제**: 첫 배포가 `[conflicting_file_path] ... "api/shared.js" has conflicts with "api/shared.css"`로 실패했다. Vercel은 `api/` 아래의 모든 파일을 함수 경로로 취급하며, 확장자를 뺀 이름이 같으면 충돌한다. `api/`의 보조 `.py` 모듈과 HTML도 같은 위험이 있다.
- **결정**: `api/index.py`는 진입점 한 줄(`from vibe_web.main import app`)만 두고, 앱 코드와 화면 파일은 `vibe_web/` 패키지(`static/` 포함)로 옮긴다. `vercel.json`의 `includeFiles`는 `vibe_web/**`를 포함한다.
- **교훈**: 계획 단계에서 Vercel의 폴더 규칙을 확인하지 않았다. 앞으로 `api/`에는 진입점 외 파일을 두지 않는다(CLAUDE.md에 규칙으로 남겼다).

## 11. 해결하지 못한 항목

- 실제 Neon 접속 검증: 이 환경에 연결 정보가 없다. 배포 환경에서 `/api/runs`로 확인한다.
- Vercel 요청 크기 제한과 실행 시간 제한의 정확한 값: 플랜별로 다르다. 배포 후 확인한다.
- 쓰기 계정에서 `TRUNCATE`/`DROP` 권한 제외: Neon 역할 설정으로 사용자가 직접 한다.
